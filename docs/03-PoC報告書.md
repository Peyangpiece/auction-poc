### 8.1 「うりきり」と最低落札額（発注者の選択: 金額を公開して実装）

発注者の説明: うりきりは、出品者が決めた最低落札額を上回ったときに光る。権利は、最高入札者のときに光る。落札者の条件は、うりきりと権利の両方が光っていること。

実装した内容:

- ロットに「最低落札額」を任意で設定できる。金額は、参加者全員の画面にそのまま表示する（隠さない）。
- 現在価格が最低落札額**以上**になると「うりきり」が点く。最低落札額のないロットは、最初から点いている。
- 締めのとき、最高入札者がいて（権利）、かつ「うりきり」なら落札。入札があっても最低落札額に届いていなければ流札（理由 `reserve_not_met`）。入札の記録は残る。
- 強制終了からの復旧でも、同じ条件で判定する。
- 最低落札額は、開始価格以上で、価格の段に乗っている金額だけを受け付ける。開始価格と同じ額は「設定なし」と同じに扱う。

仮に決めた点（確認をお願いします）:

| # | 内容 | 仮の扱い |
|---|---|---|
| 1 | 「上回る」は、ちょうど同じ額を含むか | 含む（最低落札額ちょうどで点く）。「この額なら売る」という金額だと読んだ |
| 2 | 画面の言葉 | 「最低入札額」（次に入札できる額）と「最低落札額」が紛らわしいので、画面では前者を「次の入札額」と表示した。拒否の文言（FR-BID-012）は仕様どおり「最低入札額」のまま |
| 3 | 届かずに流札になったロットの次点・繰り上げ | 何もしない（本仕様の繰り上げは、落札の後の解除が前提） |

本仕様（第2部）で直す必要がある箇所: FR-ITEM-001（最低落札価格は設けない → 公開する形で設けられる）、FR-CLS-002 と用語集の「落札」「流札」の定義、4.2 の対象外の表、AC-FR-CLS-002 の受け入れ基準、FR-UI-007（権利表示に「うりきり」を加える）。
4.2 と 12.5 の 3 が作らないとしているのは「他の参加者に金額を見せない最低落札価格」で、金額を公開する今回の形はその対象ではありません。ただし特許との関係は弁理士の確認を受けていません。

## 9. ライブ画面の 4:3 固定と、Apple のガイドラインに基づく見直し（発注者の指示）

### 9.1 ライブ画面は常に 4:3

入札画面のライブ画面の枠を、再生中も停止中も 4:3 に固定しました。ヘッドレスのブラウザで、スマホ幅・PC 幅、停止中・再生待ちのどれも 幅÷高さ＝1.333 であることを測って確かめています。

- 映像そのものは、元の比率のまま枠に収めます（切り取りも引き伸ばしもしない）。OBS の出力が 16:9 だと、枠の上下に黒い帯が出ます。帯をなくすには、OBS の出力を 4:3（例: 1440×1080）にしてください。
- 会場参加（映像なし）と、「映像を表示する」を切った場合は、枠ごと出しません。
- スマホでは、4:3 の映像の下に価格が来てスクロールが要るので、画面の下に固定した入札の帯に、現在価格と「うりきり」「権利」を小さく出しました。

### 9.2 見直しに使ったもの

指定のスキル（`dickwu/apple-design-skill`。Apple の Human Interface Guidelines を取り込んだレビュー用）を使いました。
このスキルは、Web アプリには「原則と基礎（アクセシビリティ・色・文字・配置・文言）は当てはめ、Apple 固有の部品の決まりは当てはめない」としています。

| 直した点 | 根拠（スキル内のページ › 見出し） |
|---|---|
| ライブ画面は元の比率のまま収める。停止中は黒い画面に短い文言だけ | `playing-video.md › Best practices`、`› Loading content` |
| 青（操作の色）を、押せるものだけに使う。落札の表示や価格の動きから青を外した | `color.md › Best practices`「同じ色に別の意味を持たせない」、`layout.md › Visual hierarchy`「操作と内容を見分けられるようにする」 |
| 「うりきり」「権利」を価格の直下に同じ幅で並べ、印（●／○）と文字でも状態を示す | `color.md › Inclusive color`「色だけで伝えない」 |
| コメントの切り替えの文言を、状態で変えない（「コメントを表示」に固定） | `toggles.md › Best practices` |
| 応札／観戦の前に「参加のしかた」と示し、2つの幅をそろえた | `segmented-controls.md › Best practices`、`› Desktop` |
| 本文をスマホで 17px、太字を一段細くして、大きさと太さで階層を付ける | `typography.md › Specifications`、`› Conveying hierarchy` |
| 「受付中」の点滅をやめた | `accessibility.md › Cognitive`「速く動く・点滅する動きに注意する」 |
| 背景を無彩色の灰色に、影を薄い輪郭に変えた | 実装者の判断（スキルの「ありがちな見た目になっていないか」の観点。暖色の生成り＋強い影をやめた） |

そのままにした点: ぼかしは、画面の上に浮く帯（入札の帯・上の帯）だけに使っている（`materials.md`）。明暗の切り替えは端末の設定に従い、画面には切り替えを置いていない（`dark-mode.md › Best practices`）。取り消せない操作には確認と「やめる」がある（`feedback.md`）。

確かめていないこと: 実機での見え方、文字を最大にしたときの崩れ、スクリーンリーダーでの読み上げ。

## 10. 画面の全面的な作り直し（発注者の指示）。7 章・9.2 の見た目の記述は、この章で置き換える

### 10.1 方針

- **NEWS のサービスだと分かること**: 株式会社NEWS のコーポレートサイト（News-HP）に合わせた。エンブレム（NEWS 3R）と社名をヘッダーと入場画面に置き、色・書体・角丸・ボタンの形を同じにした。
  - 色: 白地、紺 #242a5e を要所に、赤 #d24040 は細い線だけ。
  - 書体: 日本語は BIZ UDゴシック、数字と英字は Inter（55章で、日本語を Noto Sans JP に変えた）。
  - 角丸 6px、ボタンは太字・高さ 48px。
- **しるしは1つ**: 競り場の「表示板」。紺の板の上端に赤い細線（エンブレムと同じ配色）、大きな数字、2つのランプ（うりきり・権利）。
- **引き算**: カード・ピル・見出しの上の小さなラベル・数値のタイルをなくした。面は「白い地」と「紺の板」の2種類だけで、区切りは余白と細い線。

### 10.2 何を削り、何をまとめたか

## 11. 最低落札額の金額を、参加者に見せない形に変更（発注者の指示）。8.1 の「金額を公開して実装」は、この章で置き換える

発注者の指示により、「うりきり」の基準になる最低落札額の金額を、参加者には表示しないようにした。

- 最低落札額の金額は、**進行役にだけ**送る。会員の端末には、どのメッセージ（ロットの追加・状態の変化・結果・入場時・取り直し）でも金額の項目を送らない。画面で隠すのではなく、送らない。
- 会員に伝わるのは「うりきり」のランプ（届いたかどうか）だけ。届く前は「最低落札額に未達」、届いたら「この価格で売り切り」と出る。
- 入札額・現在価格・入札の履歴は、これまでどおり全員に全桁を公開する。変えたのは最低落札額だけ。
- 進行コンソールでは金額が見え、「参加者には非表示」と明記している。
- 自動テストで、会員に届いたメッセージのどれにも金額の項目が含まれないことを確かめた（進行役には届くことも確かめた）。

**本仕様（第2部）との関係。これは決定事項の変更に当たる。**

- FR-ITEM-001 と 4.2 は「他の参加者に金額を見せない最低落札価格」を作らないと決めている（【決定 v0.11】。特許に触れないという決定 v0.3 から、念のため）。今回の形は、まさにこれに当たる。
- 12.5 の特許の表にある必須要素は、入札額を見せない封印入札と、入札額の並べ替え・一部の桁だけの公開。最低落札額は入札額ではないので、表の文言には当たらないと私は読んだが、これは弁理士の確認ではない。仕様書自身も、新しい機能は確かめるか弁理士の確認を受けるとしている（12.5 の 4）。
- したがって、本番に入れる前に、(1) FR-ITEM-001・4.2・FR-CLS-002 を発注者の決定として書き換えること、(2) 弁理士の確認を受けること、の2つが要る。PoC では指示どおり実装した。

**参加者が推測できること**（仕組みの上で避けられない）: 「うりきり」が点いた瞬間の価格から、最低落札額がその価格以下であることは分かる。届かずに流札になれば、最低落札額が最後の価格より高かったことも分かる。

## 12. 配信の自動停止をやめる（発注者の指示）

発注者の指示: 競りがないときは商品の状態の説明などをするので、配信の自動停止はなくす。

- 競りがない状態が続いても、配信は止めない。止めるのは、進行役が進行コンソールで「配信を停止」を押したときだけ。
- 競りを始めるときに配信が止まっていれば、自動で開始する動きは変えていない（配信準備中 → LIVE → 受付中）。
- 進行コンソールから、「自動停止まで」の表示と、待ち時間の設定欄をなくした。
- 仕組みそのものは残してある。環境変数 `POC_AUTO_STOP_MS` にミリ秒を指定したときだけ働く（既定は 0＝止めない）。元の仕様に戻して比べたいときのため。
- 自動テストで、既定の設定では落札の後も配信が続き、「配信を停止」で止まることを確かめた。

**本仕様（第2部）との関係。これは決定事項の変更に当たる。**

- FR-STR-003 と決定事項「配信は競りの操作に連動して自動で開始・停止する」のうち、**自動で停止する**部分をやめることになる。自動で開始する部分は残る。
- 未決事項 OQ-05（配信を止めるまでの時間）は、不要になる。
- PoC の検証 P1-2（自動停止の測定）は、対象外になる。P1-1・P1-3〜P1-6 は変わらない。
- 中断が長引いたときに配信を止めるという決定（v0.11）も、同じく働かなくなる。

**費用への影響**（本仕様 13.1 の単価からの計算。実測ではない）:

- 送信の費用は、配信している時間で決まる。開催の間（9時間）ずっと流すと、Advanced HD で $0.85 × 9 時間 ＝ $7.65／開催（1ドル＝150円で約 1,150 円）。月2回で約 2,300 円。
- 本仕様 13.1 の「HD 配信＋Lightsail」の試算（月額 約 4,900〜7,300 円）が、休憩中の停止をどれだけ見込んでいるかは、仕様書からは読み取れない。自動停止がなくなる分、送信の費用は試算より増える可能性がある。
- 視聴の費用（1人1時間あたり $0.092）も、参加者が映像を見ている時間が延びる分だけ増える。
- 昼休みなど長い休憩では、進行役が「配信を停止」を押せば止められる。止め忘れを知らせる仕組みは、いまはない。

- 権限はサーバーで確かめる。監査ログは、データベースの仕組みで、消すことも直すこともできない

### 16.2 商品は競りの最中にその場で登録する。審査・事前登録・カタログは持たない（発注者の決定）

発注者の決定: 「商品はオークション中にその場で登録する」「審査はなくして、事前登録とカタログの画面も削除」「出品禁止の言葉の確認は不要」。

- 商品の登録は、進行コンソールの「品を追加」だけで行う（品名・開始価格・最低落札額）
- 審査はない。出品禁止の言葉の確認もない（いったん入れたが、発注者の決定で削除した）。登録したことだけを監査ログに残す（`lot.create`）
- 事前の商品登録、写真のアップロード、審査、開催ごとのカタログは、画面・API・データの表ごと削除した

**本仕様とのずれ（仕様書の改訂が要る）:**

| 要件 | 本仕様 | 発注者の決定による実装 |
|---|---|---|
| FR-ITEM-001 | 商品の登録項目（説明・数量・サイズ・状態・放出品の情報など） | 品名・開始価格・最低落札額だけ |
| FR-ITEM-002 | 写真（JPEG・PNG・WebP、10MB、20枚） | 持たない（商品は映像で見せる） |
| FR-ITEM-003 | 開催の前にカタログを公開する | 持たない。送料と返品特約の表示は、トップページに移した |
| FR-ITEM-004 | 商品の状態（下書き・審査待ち・承認済みなど） | 持たない（品の状態だけ） |
| FR-ITEM-005【決定 v0.11】 | 承認する人は、登録した人と別のアカウント | 審査そのものを持たない |
| FR-ITEM-006・007 | 禁止語の警告を審査の画面に出し、審査の記録を残す | 持たない。出品してよい品かどうかは、システムの外で、進行役が判断する |
| FR-ITEM-008【決定 v0.11】 | 承認後の変更で審査待ちに戻る | 審査がないので、当てはまらない |
| FR-ITEM-009【決定 v0.11】 | 再出品は、元の商品を参照する新しいロット | 商品の台帳がないので、同じ品名でもう一度登録する |

気を付ける点（事実として）: 出品してよい品かどうかを確かめる仕組みは、システムの中にはない。確認は、運用（人）で行う。

### 16.3 まだ本物ではない部分・決まっていないこと

- **SMS とメールは、実際には送っていない。** 送信サービスが未選定（本仕様 6章）のため、`data/outbox/outbox.ndjson` に書き出すだけ。送る部分は差し替えられる形にしてある（`server/src/mvp/notify.js`。失敗時は3回まで再送し、だめなら管理者への知らせに残す）

- 開催は、登録と公開の印まで。カタログがなくなったので、「公開」はいまのところ、どの画面にも影響しない（参加手続きと結び付けるのは MVP の 3）
- 進行コンソールは、PoC の合言葉の URL で入る形のまま。スタッフのログインとの結び付けは MVP の 3
- 会員の利用停止は、記録と表示まで。入札を止める結び付けは MVP の 3
- 会員による登録内容の変更、退会、スタッフの認証アプリの再発行は未実装
- 認証アプリの登録は、鍵の手入力（QR コードの表示は未実装）
- 本物の個人データは使っていない。確認はすべて架空のデータで行った

## 22. 買歩銭 10%（発注者の指示）

買歩銭は、落札者が落札額に上乗せして払う手数料。発注者の決定で、落札額の 10% とした。

### 22.1 できること

| 内容 | 補足 |
|---|---|
| 落札の明細ごとに、買歩銭（落札額 × 10%）を計算して持つ | 1円未満は切り捨て【前提】。入札の単位が500円・1,000円なら、端数は出ない |
| 落札者が払う金額は、落札額＋買歩銭。精算・消し込み・請求書・マイページのすべてで、この金額を使う | 振込の消し込みは、落札額＋買歩銭と一致する入金だけ |
| 請求書には、落札した品の行のあとに「買歩銭」を1行で載せる | 発注者から示された見本と同じ並び。消費税は、買歩銭を含めた合計に対する 10% の内税 |
| 入札の前に分かるように、トップページ・参加手続きの画面・入札画面の中に「落札額のほかに、買歩銭（落札額の10%）がかかります」と出す | 落札の知らせのメールにも、買歩銭と払う金額を書く |
| 繰り上げの落札にも、同じ割合でかかる。違約金・遅延損害金にはかからない | ― |
| 割合は、管理画面の「設定」で変えられる | 変えても、すでに落札した品の金額は変わらない |

### 22.2 仮に置いたこと・決まっていないこと

- **開発・運営者の手数料（5%）の対象には、買歩銭を含めていない【前提】。** 本仕様の手数料の式は「税込落札額の合計 × 5%」（FR-FEE-001。決定）で、買歩銭は落札額ではないため。含めるなら、式の見直しが要る
- 買歩銭の消費税の扱い（内税 10%）は、見本の請求書に合わせた。税理士の確認は受けていない【未検証】
- 入札画面の金額（現在価格・入札額）は、これまでどおり落札額だけ。買歩銭を足した金額は、落札のあとに出る
- 法人と個人で割合を分けることはしていない
- 利用規約・特定商取引法に基づく表示への記載は、文面が未作成のため入れていない
- 本仕様には買歩銭の定めがない。仕様書の改訂が要る（FR-INV・FR-PAY・FR-FEE・FR-UI に関わる）

## 32. Cloudflare の dev ドメイン（workers.dev）で動かす（発注者の指示）

### 32.1 方式と、その理由

このアプリは、普通の Cloudflare Workers の上では、そのままは動かない。理由は3つある。

- データベース（SQLite）を、Node.js 用の部品（better-sqlite3）で、ファイルに書いている
- 請求書（PDF・Excel）や書き出しを、ファイルとして置いている
- 入札の通信（WebSocket）を、1つのサーバーが全員分まとめて受けている

そこで、アプリを作り変えずに済む **Cloudflare Containers** を使う。同梱の `Dockerfile` で組み立てたコンテナを Cloudflare に置き、入口の Worker（`cloudflare/worker.js`）が、届いた通信（画面・API・WebSocket）を、そのままコンテナへ渡す。URL は `https://reiwa-no-seri.<アカウントのサブドメイン>.workers.dev` になる。

足したもの:

| ファイル | 役割 |
|---|---|
| `wrangler.jsonc` | Cloudflare の設定（名前、コンテナ、お試し用の切り替え） |
| `cloudflare/worker.js` | 入口。必ず同じ1台のコンテナへ渡す（データベースが1つのため）。外から見たサイトの名前と HTTPS であることを、アプリへ伝える |
| `Dockerfile`（変更） | 起動のたびに、最初の主催者管理者がいなければ作ってから、サーバーを動かす |
| `tools/setup-first.js`（変更） | 管理者の最初のパスワードを、環境変数 `POC_ADMIN_PASSWORD`（12文字以上）で受け取れる |

### 32.2 データを残す仕組み（発注者の指示「データが消えないように」）

Cloudflare の公式の説明では、コンテナのディスクは一時的なもので、コンテナが止まると、次は真っさらなディスクで始まる。そこで、データを、Cloudflare の消えない保存先（R2 のバケット `reiwa-no-seri-data`）へ自動で保存し、起動のたびに戻すようにした。

| 場面 | 動き |
|---|---|
| 動いているあいだ | 2秒ごとに、書き込みがあったかを見る。あれば、データベースの整合の取れた写しを取り、圧縮して R2 へ送る。請求書・印鑑の画像・送信の控えなどのファイルも、変わったものだけ送る |
| 止まる直前（通信が途絶えたとき・配り直し・Cloudflare 側の都合） | Cloudflare が停止の合図（SIGTERM）を送る。アプリは、まだ送っていない分を送ってから止まる |
| 起動のとき | R2 から、データベースとファイルを戻してから、サーバーを動かす。**R2 に届かないときは、起動しない**（空のデータで立ち上がって、R2 の中身を上書きするのを防ぐ） |
| 1時間に1回まで | その日の控え（`history/auction-年月日.db.gz`）を別に置く。壊れたとき・まちがえて消したときに、前の日の状態を取り出せる（戻す操作は手作業） |

足したもの: `server/src/persist.js`（保存と復元）、`tools/persist-restore.js`（起動の前の復元）、`cloudflare/store.js`（R2 への出し入れ）。コンテナからは、内部の名前 `store.internal` あての通信として R2 を呼ぶ。この通信は Worker が受けるので、外のインターネットには出ず、R2 の鍵をコンテナに持たせる必要もない。保存の状態は `/healthz` の `persist`（最後に保存した時刻、失敗の内容、未送信があるか）で見られる。

**残る限界（正直に書く）:**

- 合図なしに突然止まった場合（機械の故障など）は、直前の最大2秒ほどの書き込みが失われることがある。合図のある停止では失われない。これを完全になくすには、データベースそのものを Cloudflare の保存先の上に作り変える必要がある（未着手。規模が大きい）
- R2 への保存が失敗し続けているあいだは、その分が R2 に入っていない。失敗はログと `/healthz` に出るが、スタッフの画面には出していない
- 管理者のパスワードが入るまでは、Worker が「準備中」を返して、コンテナを動かさない（だれも入れない管理者が、消えないデータとして残るのを防ぐ）
- `DEMO` が `1` のあいだは、認証番号が画面に出る。**SMS の送信サービスをつなぐまでは、本物の会員の登録には使えない**（32.4）。データが残ることと、本番で使えることは、別の話である

### 32.3 配る手順

要るもの: Cloudflare のアカウント（Containers と R2 が使える契約【未検証: 条件は Cloudflare の料金のページで確かめること】）。

**方法 A: GitHub から配る（パソコンに Docker が要らない）**

1. Cloudflare の管理画面で、API トークンを作る（Workers・Containers・R2 を編集できる権限）。アカウント ID も控える
2. GitHub のこのリポジトリの Settings → Secrets and variables → Actions に、次の3つを入れる（値は、ソースにもチャットにも書かない）
   - `CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`、`ADMIN_PASSWORD`（管理者 admin の最初のパスワード。12文字以上）
3. `deploy/cloudflare` ブランチへ push する（`.github/workflows/deploy-cloudflare.yml` が動き、バケットを作り、コンテナを組み立てて配り、パスワードを入れる）
4. 終わると、Actions のログに URL（`https://reiwa-no-seri.<サブドメイン>.workers.dev`）が出る。数分待ってから開く

**方法 B: 手元のパソコンから配る**（Node.js 22 と、動いている Docker が要る）

1. `npm install` → `npx wrangler login`
2. `npx wrangler r2 bucket create reiwa-no-seri-data`
3. `npx wrangler deploy`
4. `npx wrangler secret put ADMIN_PASSWORD`

スタッフのログイン: ID `admin`、パスワードは上で入れたもの。認証コードは、お試し用のボタンで入る（31.2）。パスワードは、最初に管理者が作られたときのものが、データとして残る。あとから秘密の値を変えても、ログインのパスワードは変わらない（変えるときは、スタッフの画面から再発行する）。

### 32.4 お試し用の設定について

`wrangler.jsonc` の `DEMO` が `1` のあいだは、31.2 のお試し用の設定で動く（認証番号を画面に出す。今日の開催を自動で作る）。URL を知っている人は、だれでも、好きな電話番号で会員登録できる。スタッフの画面は、`ADMIN_PASSWORD` を知らなければ入れない。**本物の個人データは入れないこと。**

### 32.5 確かめたこと・確かめていないこと

- 確かめた: `wrangler deploy --dry-run` で、設定ファイルが読み込まれ、コンテナの組み立ての段まで進むこと。入口の Worker が付けるのと同じヘッダー（`x-forwarded-host`・`x-forwarded-proto`、Host は内部の名前）を付けてサーバーに通信し、トップページ・API・WebSocket が通ること、よそのサイトからの操作（Origin が違うもの）は 403 で断ること、クッキーに Secure が付くこと。`POC_ADMIN_PASSWORD` で管理者が作られ、そのパスワードでログインの確かめが通ること。保存と復元: Cloudflare の実行環境の手元版（workerd と R2 の模擬）に `cloudflare/store.js` を載せ、コンテナと同じ起動の順でサーバーを動かして、(1) 会員登録の3秒後に強制終了 → 真っさらな置き場で起動 → 会員・管理者・開催が戻る、(2) 会員登録の直後に通常の停止 → 次の起動で、その会員が残っている、を確かめた。自動テスト 80 件（保存と復元の4件を足した）。
- 確かめていない【未検証】: 実際の Cloudflare への配置と、workers.dev の URL での動作（この開発環境からは Cloudflare の API に届かず、Docker も動かせないため）。`Dockerfile` での組み立て。コンテナの大きさ（`INSTANCE_TYPE` は `standard-1` にしてある。前の版の `basic` は、Cloudflare に無い値で、誤りだった）で足りるか。コンテナから `store.internal` あての通信が、実際に Worker に届くこと。GitHub からの配置（方法 A）。入札の通信がつながっているあいだ、コンテナが「通信あり」と扱われて止まらないか。パスワードがコンテナに渡ること。
- 設定の書き方は、Cloudflare の公式の説明（Containers の Get started、WebSocket の例、FAQ。2026年11月時点）に合わせた。

## 37. メールアドレスでのログインと、会員登録の画面の作り替え（発注者の指示）

### 37.1 メールアドレスでもログインできる

ログインの入力欄を「携帯電話の番号 または メールアドレス」の1つにした。メールアドレスを入れると、認証番号（6桁・5分）をメールで送る。パスワードは、これまでどおり使わない。

- **仕様とのずれ**: 本番仕様では、会員のログインは「電話番号と SMS の認証番号」だけだった。発注者の指示で、メールを足した
- メールでログインできるのは、**確認のリンクを開いて確認が済んだアドレスだけ**。理由: 登録のときに打ちまちがえたアドレスが他人のものだった場合、その他人が会員になりすませてしまうため。確認が済んでいないアドレス・登録のないアドレスにも、同じ返事をする（登録の有無を、外から調べられないようにする）
- 同じアドレスの会員が2人以上いる場合は、メールではログインさせない（だれのことか決められないため）。電話番号では、これまでどおり入れる
- 送る回数の上限（1時間に5回）、番号の誤りの上限（5回）は、SMS と同じ
- メールの送信サービスは、まだつながっていない（控えに書き出すだけ）。お試し用の設定では、認証番号と、確認のリンクを、画面に出す

### 37.2 会員登録の画面（通販サイトなどの一般的な形に合わせた）

| 変えたところ | 内容 |
|---|---|
| お名前 | 「姓」「名」に分け、フリガナ（セイ・メイ）を足した。ひらがなで入れても、カタカナに直す。フリガナは、銀行振込の名義との照合に使える |
| ご住所 | 郵便番号・都道府県（選択）・市区町村と番地・建物名と部屋番号（任意）に分けた |
| 郵便番号 | 7桁入れると、都道府県と市区町村・町名を自動で入れ、番地の入力へ進む。全角の数字や、ハイフンつきでもよい。1つの番号に町名がいくつもある場合は、候補から選ぶ。見つからない場合は、手で入れられる |
| 必須・任意 | 各欄に「必須」「任意」の印を付けた。入力の例（薄い文字）も入れた |
| 配送先 | 「配送先は、上の住所と同じ」に印が付いているあいだは、欄を出さない |

## 38. 配り直しても、画面が前の版のままだった不具合（修正）

**起きたこと:** 配置（deploy）は成功と出るのに、公開サイトの画面が、前の版のまま変わらなかった（発注者の報告で分かった）。

**原因:** Cloudflare に新しい版のコンテナを置いても、**すでに動いているコンテナは、止まるまで前の版のまま動き続ける**。コンテナが止まるのは、通信が30分途絶えたときだけなので、画面を開いているあいだは、入れ替わらなかった。配置の「成功」は、置けたことを言っているだけで、動いている版が替わったことまでは確かめていなかった。それまでの「反映しました」という報告は、この点で誤りだった。

**直し方:** 配置のたびに、その版の印（`BUILD`。コミットの番号）を Worker に渡す。入口の Worker は、覚えている印と違うときに、動いているコンテナへ止める合図を送り（アプリは、未送信のデータを R2 へ送ってから終わる）、新しい版で立ち上げ直す。入れ替えのあいだ（数秒〜数十秒）は、つながっている入札の通信が切れる。**開催の最中には、配り直さないこと。**

【未検証】この入れ替えが、実際の Cloudflare の上で期待どおりに動くこと（この環境からは、公開サイトに届かない）。発注者の画面で確かめてもらう。

## 39. 会員登録も、メールアドレスで始められる（発注者の指示）

会員登録の最初の欄を「携帯電話の番号 または メールアドレス」にした。メールアドレスを入れると、認証番号をメールで送る。

- メールで確かめた人は、「お客様の情報」で、携帯電話の番号を入れてもらう（当日の連絡と配送に使う）。メールアドレスは、確認済みとして登録する（確認のメールは送らない）
- 電話で確かめた人は、これまでどおり、メールアドレスを入れてもらう
- **仕様とのずれ**: 本番仕様では、会員登録は SMS の認証が前提だった（FR-AUTH-001「1つの電話番号で登録できる会員は1人」）。「1つの電話番号に1人」は今も守るが、メールで登録した人の電話番号は、**本人のものと確かめていない**
- そのため、未確認の電話番号は、SMS でのログインには使わせない（その番号の本当の持ち主が、他人の会員に入れてしまうのを防ぐ）。ログインは、メールアドレスで行う。マイページに「未確認」と出す。受付で本人を確かめて番号を変えると、確認済みになる
- 【要確認】他人の電話番号を先に入れられると、その番号の本当の持ち主が、SMS で登録できなくなる（「この電話番号は登録済みです」と出る）。受付での番号の変更で直せるが、本人が SMS で確かめたら自動で入れ替える、などの扱いを決める必要がある
- B2C の SMS の上限など、電話番号を数える決まりがある場合、メールでの登録はその数え方の外になる

確かめたこと: 自動テストを1件足した（メールでの登録、電話番号の重なり、未確認の番号でのログインの断り）。実際のブラウザで、メールでの登録 → 途中での読み込み直し → 登録の完了までを通した。

38 章の入れ替えの不具合は、発注者の画面で、新しい版（フッターつき）に替わったことを確かめてもらった。

## 40. 参加の前に、オンラインか会場かを選ぶ（発注者の指示）

「競りに参加する」を押すと、まず「オンラインで参加」「会場で参加」の2択を出す。選んだあとで、受け取り方法と支払方法を聞く画面に進む。選び直すこともできる（手続きを済ませる前まで）。

- 会場の QR コードから来た人は、会場参加に決まっているので、2択は出さない（これまでどおり）
- 「会場で参加」を選ぶと、当日現金も選べる。「オンラインで参加」は、銀行振込だけ
- **仕様とのずれ**: 本番仕様では、会場参加は「会場の QR コードから来た人だけ」（FR-MODE-002）だった。画面で選べるようにしたので、会場にいない人も「会場で参加」を選べてしまう。ただし、会場参加の人は、**受付係の来場確認が済むまで、入札の画面に入れない**（これは変えていない）。会場にいない人がまちがえて選ぶと、入れないままになるので、その場合は受付（主催者）に連絡して直してもらう必要がある【要確認: まちがえて選んだ人が、自分でオンラインに直せるようにするか】

確かめたこと: 自動テストを1件足した（画面で会場を選んだ人は会場参加になり、来場確認の前は入れない）。画面の通し確認に、2択の表示・会場を選ぶと当日現金が選べること・選び直しを足した。

### 40.1 まちがえて「会場で参加」を選んだ人は、自分でオンラインに直せる（発注者の決定）

来場の確認を待つ画面に、「会場に行かない場合: オンライン参加に切り替える」を置いた。押すと、その場でオンライン参加になり、入札の画面に入れる。参加番号は変わらない。当日現金を選んでいた場合は、銀行振込に変わる（その旨を画面に出す）。記録（監査ログ）に残る。

- 受付係の来場確認が済んだあとは、切り替えられない（会場で札を受け取っているため。受付に申し出てもらう）
- **仕様とのずれ**: 本番仕様では、1回の開催の中で参加モードは変えられない（FR-MODE-004）。来場確認の前に限って、会場からオンラインへ、本人が変えられるようにした。オンラインから会場への変更は、これまでどおり、受付係の来場確認で行う

### 40.2 入札の画面からも、会場参加に切り替えられる（発注者の指示）

オンライン参加で入っている人の入札の画面に、「参加のしかた: オンライン参加　会場参加に切り替える」を置いた。押すと確かめのダイアログが出て、切り替えると、来場の確認を待つ画面に戻る（そこから、オンライン参加に戻すこともできる）。

- 切り替えたあとは、受付係の来場確認が済むまで、入札できない（別のタブを開いたままにしていても、入札は断る）
- 会場参加で来場確認が済んでいる人には、切り替えを出さない（オンラインへ戻すときは、受付に申し出てもらう。当日現金の精算とのずれを防ぐため）
- 40.1 と合わせて、**来場確認の前であれば、本人がオンラインと会場を行き来できる**。FR-MODE-004（1回の開催の中では変えられない）とのずれは、40.1 と同じ

### 40.3 来場確認が済んだ人も、自分でオンライン参加に戻せる（発注者の決定）

会場参加で入っている人の入札の画面にも、「参加のしかた: 会場参加　オンライン参加に切り替える」を出す。確かめのダイアログを通して切り替える。

- 切り替えると、来場確認は取り消される。会場参加に戻すときは、もう一度、受付で来場の確認を受ける
- 当日現金を選んでいた場合、お支払いは銀行振込に変わる。**すでに当日現金で精算した分は、そのまま**（精算済みのまま残る）
- 参加番号は変わらない。切り替えは、記録（監査ログ）に残る
- これで、開催の途中でも、本人がオンラインと会場を行き来できる。FR-MODE-004（1回の開催の中では変えられない）は、発注者の決定で、守らない形になった
- 【前提】会場で渡した参加番号の札の回収は、運用で行う（オンラインに戻した人が札を持ったままになる）

### 40.4 手続きが済んだ人にも、入るたびに2択を出す（発注者の指摘）

**指摘:** 「参加する」を押すと、2択が出ずに、そのままオンラインで入ってしまう。

**原因:** 2択を、その開催でまだ参加手続きをしていない人にだけ出していた。手続きが済んだ人は、前に選んだ参加のしかたのまま、入り口の画面に進んでいた（配置の不具合ではなく、作りの不足だった）。

**直し方:** 手続きが済んだ人にも、入るたびに「オンラインで参加」「会場で参加」の2択を出す。いまの参加のしかたと参加番号を、その上に出す。いまと同じほうを選べば、そのまま入札の画面に入る。違うほうを選べば、切り替えてから入る（会場にした場合は、来場の確認を待つ画面になる）。会場参加で来場の確認を待っている人には、2択ではなく、待つ画面を出す（そこから、オンラインに切り替えられる）。

## 43. 入札金額の入力欄と、その右の入札ボタン（発注者の指示）

入札の画面の表示板に、現在の価格の表示とは別に、**入札金額の入力欄**を置き、その右に**入札ボタン**を置いた。

- 入力欄には、はじめから最低入札額が入っている（そのまま「入札」を押せば、これまでと同じ1回の操作で入札できる）
- 金額を書き換えると、最低入札額より高い金額でも入札できる。数字だけを受け付け、3桁ごとに区切って表示する（全角の数字も直す）。Enter キーでも入札できる
- 入札できる金額（価格の段）に合わない金額は、送る前に断り、すぐ下とすぐ上の入札できる金額を出す（例: 「入札できる金額は、¥10,000 か ¥11,000 です」）。最低入札額に届かない金額も断る
- 最低入札額より上で、いまの価格の2倍以上になる金額は、押す前に確かめのダイアログを出す（桁の打ちまちがいを防ぐ。入札は取り消せないため）
- ほかの人の入札で価格が上がったとき: 入力欄の金額が新しい最低入札額より低くなったら、新しい最低入札額に直す。自分で書いた金額がまだ有効なら、そのまま残す
- 入力欄は、入札できるときだけ出す（観戦中・自分が最高入札者のあいだ・受付の前後は、これまでどおり、案内のボタンだけ）

**仕様とのずれ**: PoC 仕様（POC-UI-002）は「ボタンを押すだけ。最低入札額で入札する」だった。金額を入力できるようにしたので、1回の入札で価格が大きく上がりうる。サーバーの判定（段に乗っているか、最低入札額以上か、上限額）は変えていない。金額はすべての参加者に公開され、自動入札ではない（本人が、その場で金額を入れて送る）ので、特許上の制約（12.5）には触れない。

サーバーから、入札単位の表と、その品だけの入札単位を、端末に送るようにした（入力された金額を、端末の側で確かめるため。最低落札額は、これまでどおり送らない）。

確かめたこと: 実際のブラウザで、最低入札額のまま入札、段に合わない金額の断り、全角の入力、2倍以上の金額の確かめ、高い金額での入札と相手側の入力欄の更新を通した。

## 45. 映像のない間の、待機のアニメーション（発注者の指示）

映像のない間（準備中・停止中。休憩中も同じ枠）、映像の枠に、レイワのシンボルのバッジが跳ね上がりながら回るアニメーションを出す。発注者の決定: 回る向きは地球の自転の向き、動きの作りは任せる、文字は残す、準備中・休憩中・停止中のどれにも出す。

- **動き**: ためる（少し沈む）→ 伸びながら跳ね上がる → 空中で、縦の軸のまわりを1回転（手前の面が左から右へ＝地球の自転の向き）→ 落ちる → 着地でつぶれる → 小さく戻る。下の影は、高く上がるほど小さく薄くなる
- **リズム**: 1回の動きが約1秒、そのあと約1秒休む（2.2秒で1周）。発注者の最初の案は「1秒おき」だったが、隣の入札の邪魔にならないように、休みを入れた（動きの作りは任された）
- **作り方**: 動画ファイルではなく、画面の上のアニメーション（CSS）。通信量が増えず、どの大きさでもくっきり出る。動かすのは位置・大きさ・回転と濃さだけで、端末に負担をかけない
- **文字**: バッジの下に「映像を準備しています」「映像は停止中です」を残した
- **「動きを減らす」設定の端末**: 動かさず、止まったバッジを出す
- 42 章で「飾り」として外した紋章を、発注者の指示で、動く形で戻した

【未検証】After Effects 関連の Skill を使う指示だったが、この環境には無かった（検索しても見つからなかった）。代わりに、ウェブのアニメーション設計の Skill（緩急の付け方、動かす性質の選び方、動きを減らす設定への対応）に沿って作った。実機での滑らかさは、確かめていない。

【要確認】動きが5秒より長く続くものには、止める手段を用意するのが、アクセシビリティの基準（WCAG 2.2.2）である。いまは、端末の「動きを減らす」設定でだけ止まる。画面の中に止めるボタンを置くかどうかを、決める必要がある。

### 45.1 コインのように、厚みを持たせた（発注者の指示）

バッジを、表の面・裏の面・側面からなる、厚みのあるコインにした。回っている途中で、金色の側面（濃淡を交互にした、ふちの刻み）と、裏の面が見える。

- **GLB ファイル（3D のモデル）は作らなかった。** GLB を出すには、3D を描くための部品（数百 KB）を読み込む必要があり、通信量が増え、いまの読み込みの制限（外の部品・画面に直接書いたスクリプトを許さない）とも合わせにくい。同じ見た目は、画面の立体の機能（CSS の 3D）だけで作れるので、そちらにした
- 作り: 表と裏の面を、厚みの分だけ前後に離して置き、そのあいだに、細い板 40 枚を円く並べて側面にした。厚みは、直径の 10%
- 裏の面にも、同じシンボルを出す（裏返っても、文字は鏡文字にならない）

## 46. 角の丸みを、Apple のデザインにそろえた（発注者の指示。画面の細部の Skill を使用）

ボタン・入力欄・各セクションの角を、全画面でそろえた。それまでは、どの部品も 6px の小さな丸みだった。

| 部品 | 丸み |
|---|---|
| 小さな印（「必須」「任意」など） | 6px |
| ボタン、入力欄、選択の枠、応札／観戦の切り替え、案内の帯 | 12px |

| 丸い部品（コイン、日付の丸、スイッチ） | これまでどおり、円 |

### 51.2 確認コードは、無い（発注者の決定）と、その危なさ

はじめは、最初のログインに確認コードを足していた。発注者の指示で、消した。**そのため、登録されたメールアドレスを知っている他人が、本人より先にパスワードを決めると、その人がスタッフとして入れる**（メールアドレスの持ち主であることは、確かめていない）。弱める手立ては、次のとおり。

- 決められるのは、登録から7日のあいだ、パスワードがまだ無いときだけ。決めたあとは、上書きできない
- だれが、いつ決めたかは、記録（`staff.setup`）に残る。本人が決めようとして断られたら、先に決められたと分かる → 主催者管理者が、そのスタッフを停止して、決め直せるようにする
- **運用: 登録したら、本人が、すぐにパスワードを決める**

本番の運用の前に、メールで届くリンクからだけ決められる形（メールの送信サービスをつないだあと）に戻すことを、すすめる。【要確認】

### 51.3 最初の主催者管理者の登録

- 最初の主催者管理者のメールアドレスは、**ソースには書かない**（このリポジトリは公開されている）。代わりに、メールアドレスの SHA-256 だけを、設定（`wrangler.jsonc` の `ADMIN_EMAIL_SHA256`）に置く。そのメールアドレスで「はじめての方」から進むと、主催者管理者として登録され、パスワードを決められる（1回だけ）

確かめたこと: 自動テストを2件（登録 → 登録の無いメールアドレスの断り → パスワードを決めてログイン → ハッシュで保存されていること → 決めたあとは上書きできないこと → 決め直し → 期限。設定のメールアドレスでの、最初の主催者管理者の登録が、1回だけ通ること）。

### 52.4 本番に切り替える手順

|---|---|

### 57.2 入札と落札の演出

発注者の指示で、After Effects のモーションデザインの手法に沿って作った。After Effects そのものは、この開発環境（Linux のコンテナ）では動かせない。また、After Effects で作った動き（Lottie など）を画面に入れるには、After Effects での制作と、再生の部品の追加が要る。そこで、After Effects 用のスキル（GitHub の `iart-ai/motion-design-skills` の `after-effects`・`animation-principles`）に書かれた手法と数値を、ブラウザの Web Animations と CSS で組み立てた。

| 使った手法（AE での呼び方） | どこで |
|---|---|
| 予備動作（anticipation）: 動く前に小さく逆へ | 入札: 価格が 70ms 沈んでから弾む。印・札の印: 上で大きく構えてから落ちる |
| 着地の行き過ぎ（overshoot） | 入札: 価格が 1.075 倍まで。印: 押した瞬間に 0.86 倍につぶれる |
| 慣性の揺り戻し（inertial bounce の式 `value + v·amp·sin(2π·freq·t)/e^(decay·t)`） | 価格・印・札の止まり方。式をそのまま計算して、キーフレームの列にした |
| 遅れて付いてくる動き（follow-through） | 入札: 金の輪と光の帯が 40〜100ms 遅れる。落札: 板・札が印の衝撃で揺れ、墨の輪が広がる |
| 時間差（stagger） | 落札の札: 札 → 印（0.42 秒）→ 品名（0.52 秒）→ 金額（0.58 秒） |
| 入るときは減速、出るときは加速 | `cubic-bezier(0.16, 1, 0.3, 1)` と `cubic-bezier(0.7, 0, 0.84, 0)`。消えるときはすべて加速 |
| 音と振動を、着地の瞬間に合わせる | 入札・印・落札の音は、着地の時刻に鳴らす |

| 場面 | 見え方 | 長さ |
|---|---|---|
| 自分の入札が受理された | 価格が沈んで弾み、揺れて止まる。金の輪が板の外へ広がり、光の帯が価格の上を走る。ボタンに金の面が満ちて引く。短い振動と音 | 0.9 秒 |
| 品が落札になった（だれでも） | 朱の「落札」の印が上から落ちて押され、板が揺れ、墨の輪が広がる。印に落札者の番号（自分なら「あなた」） | 1.8 秒 |
| 自分が落札した | 地が暗くなり、札が下から入る。印が押されると、押した点から金の光の筋と紙吹雪（紺・金・朱・白）が出る。品名と金額が時間差で入り、金額は数え上がる。板の印は出さない（札の印と重なるため） | 3 秒 |
